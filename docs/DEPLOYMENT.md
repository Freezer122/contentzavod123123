Цель: Ubuntu Desktop 22.04+ / совместимая версия, 4 vCPU, 8 GB RAM, 80 GB SSD. По умолчанию работает один браузерный исполнитель; максимум конфигурации — два. Реальное потребление браузеров проверяется на ваших профилях: данные mock-режима для этого не подходят.

## Хост

1. Установите Node.js 22.15+ LTS, Docker Engine с Compose plugin, Git и клиент PostgreSQL версии 17+ для резервных копий. Используйте официальные инструкции [Node.js](https://nodejs.org/en/download), [Docker для Ubuntu](https://docs.docker.com/engine/install/ubuntu/) и [PostgreSQL Apt](https://www.postgresql.org/download/linux/ubuntu/).
2. Создайте пользователя `factory`, каталог `/opt/content-factory` и передайте ему права на каталог проекта. Загрузите исходники. Команды приложения выполняются этим пользователем.
3. Установите AdsPower либо Dolphin на хост, запустите приложение в графической сессии пользователя `factory` и проверьте Local API на loopback. Не публикуйте порт API в интернет.
4. Для сервера без рабочего стола установите лёгкую среду, например XFCE (`sudo apt install xfce4 dbus-x11`), и настройте графическую сессию. Удалённый просмотр организуйте через SSH-туннель к VNC, привязанному только к `127.0.0.1`, либо через существующий защищённый удалённый рабочий стол. Устанавливайте браузер из официального пакета, совместимого с ОС.

Пример туннеля для уже настроенного локального VNC:

```bash
ssh -L 5901:127.0.0.1:5901 factory@SERVER
```

С клиентского компьютера подключитесь к `127.0.0.1:5901`. Графическая сессия должна быть авторизована и доступна после перезагрузки; systemd сам по себе не создаёт её и не запускает авторизованный AdsPower/Dolphin. Используйте поддерживаемый производителем автозапуск в этой сессии.

## Приложение и БД

```bash
cd /opt/content-factory
cp .env.example .env
chmod 600 .env
# Задайте production, токен/allowlist, секреты, БД, LLM и профиль браузера.
docker compose up -d
npm ci
npm run db:migrate
npm run db:seed
npx playwright install --with-deps chromium
npm run check
npm run start
```

Для самих публикаций используется Chromium, запущенный провайдером, а установленный Playwright Chromium нужен тестам. Compose запускает только PostgreSQL и Redis. Оба порта привязаны к loopback; данные находятся в именованных томах. Redis использует AOF, PostgreSQL — основное состояние задач. Не используйте `docker compose down -v` при обычном обновлении.

## Автозапуск

В `deploy/systemd/content-factory.service` проверьте `ExecStart` (`command -v node`), имя пользователя, каталог и значения `DISPLAY`/`XAUTHORITY` вашей графической сессии. При необходимости исправьте путь `/usr/local/bin/node` под вашу установку.

```bash
sudo cp deploy/systemd/content-factory.service /etc/systemd/system/
sudo cp deploy/systemd/content-factory-backup.* /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now content-factory
sudo systemctl enable --now content-factory-backup.timer
sudo systemctl status content-factory
journalctl -u content-factory -n 100 --no-pager
```

Docker-тома и приложения браузеров должны также восстанавливаться после перезагрузки. Проверка:

1. Поставьте тестовую публикацию на будущее, сохраните ID и время.
2. Перезапустите сервис и убедитесь, что ID сохранился.
3. Отмените другую задачу и снова перезапустите: отменённая задача не должна вернуться.
4. На отдельном тестовом аккаунте проверьте сбой перед отправкой и после неё. После барьера отправки задача должна остаться на ручной проверке.
5. Проверьте перезагрузку VPS целиком, включая графическую сессию, доступ к Local API и очистку браузеров.

Эти проверки на реальном VPS не выполнялись в среде разработки.

## HTTPS redirect

Настройте домен и сертификат TLS в Nginx. Фрагмент `deploy/nginx.conf` подключается в HTTPS server block. Публично доступен только `/r/`. `/api/` и `/health` остаются локальными и дополнительно защищены токеном.

`PUBLIC_BASE_URL` должен содержать реальный HTTPS origin без завершающего слеша. За локальным Nginx задайте `TRUST_PROXY=127.0.0.1,::1`; конфигурация должна перезаписывать `X-Forwarded-For`, как в примере. При другом сетевом расположении прокси сначала адаптируйте валидацию доверенных адресов.

## Резервные копии

```bash
node scripts/backup.mjs
```

Скрипт использует установленный `pg_dump` и `DATABASE_URL`, пишет атомарный custom dump с правами 0600 в каталог `backups/` (0700) и хранит 14 дней. Ошибочная копия не заменяет завершённую. Пароль передаётся дочернему процессу через `PGPASSWORD`, а не аргумент командной строки. Укажите `BACKUP_DIR` для другого расположения. Настройте отдельное защищённое хранение копий вне VPS.

Для тестового восстановления в целевую БД (заменяет её содержимое) сначала остановите приложение и убедитесь, что выбран правильный сервер:

```bash
sudo systemctl stop content-factory
docker compose exec -T postgres pg_restore -U factory -d content_factory --clean --if-exists < backups/CHOSEN_BACKUP.dump
sudo systemctl start content-factory
```

Проверьте `/health`, сохранённую очередь и счётчики публикаций. Redis может быть восстановлен из PostgreSQL: reconciler создаёт только задачи со статусом QUEUED и актуальной ревизией.

## Состояния при сбоях

Перед потенциальной отправкой транзакционно фиксируется SENDING. Если процесс остановился после неё, восстановление выставляет UNCERTAIN и NEEDS_REVIEW, а не повторяет публикацию. POST и COMMENT имеют отдельные состояния. Ошибка до отправки допускает не более трёх попыток с backoff для временных ошибок. Ошибки авторизации/проверок останавливают аккаунт и требуют человека.

Блокировки профилей и глобальные браузерные слоты хранятся в БД, обновляются heartbeat и ограничивают отдельные процессы. При потере блокировки открытый сеанс закрывается. Изоляция Prisma-транзакций — SERIALIZABLE. BullMQ также ограничен глобальным concurrency. Все экземпляры должны иметь одинаковое значение `BROWSER_CONCURRENCY`.

Снимки ошибок могут содержать содержимое профиля. Не раздавайте каталог `artifacts/` через HTTP. Следите за его размером и архивируйте/удаляйте старые снимки по вашей политике. Уведомления отправляются разрешённым администраторам Telegram; если Telegram недоступен, причину ищите в `system_events` и journalctl.
