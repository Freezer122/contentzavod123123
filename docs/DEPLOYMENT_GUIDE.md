# Content Factory — Ubuntu production V1.14

## Текущая установка

Новый сервер: 48.102.129.89. Пользователь приложения: `contentfactory`. Текущий релиз выбирается symlink `/opt/content-factory/current`, исходные релизы — `/opt/content-factory/releases`. Node: `/opt/content-factory/runtime/node-v22.23.5-linux-x64/bin/node`.

На Mac оператор использует SSH-конфигурацию `.local/v18/ssh_config`, alias `content-factory-v18`. Ключ и known_hosts в `.local/v18`, приватные файлы 0600/0700. Эти файлы не входят в релиз или репозиторий. Работа приложения после установки не использует Mac или SSH-туннель.

Службы:

- `postgresql`, `redis-server` — нативные, loopback, Redis AOF/everysec, DB15 для publishing.
- `content-factory-api` — HTTP `127.0.0.1:3000`; без polling и обработки очереди.
- `content-factory-telegram` — единственный long polling, allowlist 7842338078, flock и Restart=on-failure.
- `content-factory-vps-worker` — PublishingWorker и отдельный EngagementQueue.
- `content-factory-adspower` — официальный headless, без desktop/Xvfb.
- `content-factory-api-guard` — firewall для API/DB/Redis; CDP должен оставаться loopback.
- `content-factory-backup.timer` — ежедневно 03:00 UTC.
- `content-factory-maintenance.timer` — каждые пять минут.

Все основные службы и таймеры включены в автозапуск. Рестарты процессов проверены; полный reboot сервера не выполнялся. Docker Compose оставлен только как необязательный вариант разработки.

## Секреты и безопасные режимы

Текущий релиз — `/opt/content-factory/releases/20261120-v114-human`. Подключение OpenAI сохранено с V1.9. Официальный Responses API подключается дополнительными systemd drop-in `50-openai-v19.conf` для API/bot/worker. Они читают `/etc/content-factory-secrets/openai.env` (root 0600, `OPENAI_API_KEY`) и `/etc/content-factory/openai-settings.env` (root:contentfactory 0640). Ключ не помещать в worker.env, исходники, argv или сообщения Telegram.

Настройки: `LLM_PROVIDER=openai`, `POST_MODEL=gpt-6.2-sol` (low), `REPLY_MODEL=gpt-6.1-terra` (none), `BIO_MODEL=gpt-6.1-terra` (none), `LLM_MAX_TOKENS=2048`, `AI_WARNING_USD=3`, `AI_TOTAL_LIMIT_USD=5`. Дневной и месячный лимиты текущего теста также $5; прежние ограничения аккаунтов/назначений сохраняются. Накопительный предел учитывает все сохранённые расходы и резервы, смена даты его не сбрасывает.

После ротации заменить значение в защищённом файле, сохранить root 0600 и перезапустить `content-factory-api`, `content-factory-telegram`, `content-factory-vps-worker`. Не сбрасывать расходы ради повтора. Перед сменой моделей проверить доступ через `/v1/models` и цены; неизвестная модель без тарифа блокируется. Детали: [отчёт V1.9](OPENAI_V1_9_REPORT.md).

`/etc/content-factory/worker.env` — root:contentfactory 0640; содержит DATABASE_URL, Redis namespace, AdsPower API key, tracking/internal secrets. `/etc/content-factory-secrets/telegram.env` — root 0600, каталог 0700; systemd читает EnvironmentFile до смены пользователя. `/etc/content-factory/telegram.env` задаёт роль bot и allowlist; `/etc/content-factory/api.env` — api и loopback.

EnvironmentFile имеет приоритет над Environment/--setenv: для теста bot надо подключать worker.env, secret telegram.env, затем role/allowlist telegram.env. Не передавать секреты в argv, не печатать env или полный systemctl show Environment. AdsPower CLI получает собственный key через приватный launcher; его stdout маскируется.

Сейчас обязательны:

```dotenv
BROWSER_EXECUTION_MODE=DRY_RUN
BROWSER_CONCURRENCY=1
ADSPOWER_HEADLESS=1
ADSPOWER_ALLOWED_PROFILE_IDS=k1j71gt4
PROFILE_CHANGES_ALLOWED=0
ENGAGEMENT_EXECUTION_MODE=DRY_RUN
```

В PostgreSQL `factoryPaused=true`, `automationPaused=true`; Threads 02 активирован владельцем для ручной работы, manualLiveEnabled=true, automaticEnabled=false. Настройки поиска и лайков сохранены, но автоматический engagement остаётся OFF и не запускается при паузе. Снятие PAUSED само по себе не включает LIVE. Реальные посты/CTA и ответы требуют отдельного подтверждения выбранного текста через ручной режим V1.12. Сохранение био/ссылок — отдельного разрешения и подтверждения конкретного предпросмотра. Тестовые черновики и PREVIEWED jobs не должны автоматически использоваться для реальной отправки.

Не запускать Threads 02 на двух устройствах. Thread 01 не включён в allowlist исполнителя. Общий browser-slot и profile lease запрещают одновременные рабочие браузеры. Чужие/вручную открытые сессии не закрываются автоматически.

## Обновление и проверки

Собирать отдельный релиз; не копировать node_modules с Mac. `npm ci`, `npm run build`, `npm run build:tools`. Перед миграцией остановить bot/worker/API, создать согласованный backup. Применить `prisma migrate deploy` с приватным DATABASE_URL. Не добавлять marker `v15-verified-legacy-prisma-timezone`: UTC-преобразование уже выполнено. Старые миграции не редактировать.

Переключить current атомарным rename symlink, запустить три службы. Проверить `/live`, авторизованный `/health`, Telegram-команды, PAUSED/DRY_RUN и отсутствие открытого браузера. После миграции timestamps проверить `scripts/verify-utc-v18.ts`.

Полные тесты на VPS используют `ADSPOWER_FIXTURES=1` и существующий SunBrowser через CDP, пустые incognito-контексты и HTML-фикстуры. Дополнительный Chromium не нужен. Проводить их при закрытом рабочем профиле и приостановленной фабрике. Интеграционный PostgreSQL/Redis тест — только через `deploy/test-isolated-v18.py`: отдельная `cf_v18_test_isolated` и пустая Redis DB14. Рабочая очередь — DB15, её не очищать.

`check-features-v18.ts` выполняет только READ_ONLY/DRY_RUN: ввод восстанавливается, Save/Post/Reply не нажимаются. После теста настройки engagement возвращаются; оставшиеся тестовые QUEUED jobs помечаются FAILED. Кнопка лайка проверяется отдельно `check-like-v18.ts`, без клика.

## Подготовка и поиск V1.10

Исходники сохраняются сразу, независимо от PAUSED/DRY_RUN. После выбора аккаунта текст сохраняется в `source_contents`, назначение и FSM — в `system_settings` (`flow-USER_ID`). До 20 000 символов; для большого текста доступен UTF-8 `.txt` до 80 КБ. Не писать исходный текст и секреты в журналы. `BOT_STAGE` хранит только этап, update ID, тип, размер и идентификаторы. `/start` сохраняет ввод и назначения; явное переключение сценария освобождает другой FSM.

`GenerationQueue` работает в `content-factory-vps-worker`, проверяет задания раз в две секунды. В `system_settings` сохраняются `generation-task-ID` со статусами QUEUED/RUNNING/COMPLETED/FAILED/NEEDS_REVIEW. Бот доставляет готовые предпросмотры отдельно: подготовка постов/ответов и тематический поиск не удерживают обработчик polling. Не запускать ещё один worker для той же очереди. QUEUED переживают рестарт, RUNNING переводятся в NEEDS_REVIEW без платного повтора. Перед повтором сверить `ai_requests`, сохранённый receipt и черновики. Сетевой UNKNOWN продолжает блокировать новые OpenAI-запросы.

Одобрение текста не создаёт publishing job. Новая и старая кнопки одобрения требуют отдельного подтверждения отправки. DRY_RUN блокирует реальную постановку через финальную кнопку. Права на исходник и состояние аккаунта повторно проверяет существующий Scheduler. Отклонённые черновики отправлять нельзя. Удаление исходника отменяет ожидающие генерации; при уже идущей генерации сначала дождаться результата.

Автопоиск определяется engagement.enabled, состоянием завода, аккаунта и `engagement-schedule-ACCOUNT`. Расписание содержит nextSearchAt, lastSearchAt, lastAttemptAt и последнюю ошибку. После успешного поиска следующий старт = фактическое время + 24 часа / sessionsPerDay. Пропущенные интервалы не догоняются пачкой. При ошибке браузера успешная дневная сессия не расходуется; для автопоиска сохраняется пауза 15 минут. Дневные лимиты поиска/ответов и бюджеты используют UTC; интерфейс переводит времена в TIMEZONE.

«Поиск без публикации» — отдельная ручная READ_ONLY-задача: разрешена при PAUSED и DRY_RUN, без LLM, без ответов и лайков. Она соблюдает дневной лимит, один browser-slot, allowlist и приоритет публикаций/CTA. «Сгенерировать ответы» создаёт отдельные задачи Terra только по явной команде; после поиска автоматической генерации нет. DRY_RUN не исполняет одобренные interaction jobs автоматически. Ручной DRY_RUN-предпросмотр редактора доступен отдельно.

Экран «Причины остановки» показывает состояния завода/аккаунта, ключ/модель/бюджет, расписание, кандидатов, ожидание одобрения, уже одобренные задания и ошибки. Heartbeat `engagement-queue-state` обновляется раз в минуту, включая PAUSED. До снятия паузы nextSearchAt обозначает плановое время, а не обещание запуска вопреки паузе. Существующие задания QUEUED сохраняются; их нельзя автоматически подтверждать или отправлять при проверке.

Результаты и границы приёмки: [V1.10](V1_10_REPORT.md).

## Engagement V1.11: разовая отправка

Одобрение и исполнение хранятся отдельно: APPROVED не означает PUBLISHED. PREVIEWED больше не снимает задачу с ожидания — DRY_RUN записывается отдельной отметкой. Список «Одобренные ответы» показывает ручные пользовательские одобрения; служебные записи остаются в истории.

Только после отдельного разрешения пользователя на точные account/URL/текст оператор может задать в защищённом EnvironmentFile:

```dotenv
ONE_SHOT_REPLY_JOB_ID=точный-job-id
ONE_SHOT_REPLY_USER_ID=разрешённый-telegram-user-id
ONE_SHOT_REPLY_EXPIRES_AT=UTC-ISO-время-истечения
```

По умолчанию все три значения пусты. Это адресное разрешение на один ответ, не переключатель глобального LIVE. Перезапустить службы, затем в Telegram выполнить «Опубликовать сейчас»: свежий READ_ONLY-preflight, PENDING-разрешение на пять минут и отдельное финальное подтверждение. Подтверждение без адресного gate отклоняется. Глобальные режимы оставить DRY_RUN, factoryPaused — без изменений. После выполнения/истечения убрать адресные параметры. Не разрешать для этого весь список job IDs и не включать старый backlog.

Permission связывает job/account/URL/hash/version/user/expiry. Перед submit CONFIRMED превращается в CONSUMED в одной транзакции с SENDING/PUBLISHING. Повторный submit не допускается. RUNNING-задача при аварийном рестарте требует сверки; SENDING восстанавливается как UNCERTAIN. «Проверить результат» читает интерфейс без отправки; если результата не найдено, UNCERTAIN сохраняется. Не сбрасывать его в QUEUED автоматически.

Стиль Terra — `terra-comments-v1.11`, SHORT по умолчанию, 60–220 символов и до трёх предложений. Изменение стиля не переписывает одобренное. Неподходящий новый ответ сохраняется NEEDS_EDIT/DECLINED, без дополнительной LLM-оценки или платного retry. Перегенерация требует явной команды; ручная правка требует нового одобрения.

Автоматическая отправка engagement остаётся OFF независимо от глобальных LIVE-флагов. До её отдельной реализации проверить правила Threads, ограничения аккаунта и cutover без backlog. Переход к первому LIVE-тесту не входил в V1.11. Доказательства и результаты: [V1.11](V1_11_REPORT.md).

## Логи и место

JSON-логи: `/var/lib/content-factory/logs`, секреты маскируются. `LOG_MAX_BYTES` ограничивает текущий файл (по умолчанию 10 MiB); root logrotate-конфиги в `/etc/logrotate.d/content-factory-*` задают normal 7d/debug 3d/critical 30d и maxsize 10M. Journald: SystemMaxUse 200M, RuntimeMaxUse 50M, max age 7d.

Maintenance чистит только диагностические reports/artifacts и app tmp, обычные 7d/debug 3d/critical 30d. KEEP, связанные с незавершённым UNCERTAIN, пользовательские media, профили/cookies, БД и backups не удаляются. Симлинки не обходятся. Ошибка авторизации/challenge помечается критическим errorCode. Место <20% — уведомление; <10% — критическое, новые тяжёлые browser-задачи блокируются. Оповещение повторяется не чаще раза в сутки на одном уровне.

## Бэкапы и восстановление

Обычные daily copies: `/var/lib/content-factory/backups/daily`, до семи последних; KEEP-снимки отдельно. До расширений создан отдельный `KEEP-before-v18-extensions`. При критическом диске новый backup останавливается с ошибкой, требует реакции оператора; старые KEEP не удаляются автоматически.

Согласованный migration archive сохранён на старом VPS, новом VPS и Mac. На Mac дополнительно создан AES-256-GCM архив `.local/v18/private/KEEP-v18-transfer.tgz.enc`; ключ `.local/secrets/v18-backup.key` 0600. Расшифрование проверено, SHA256 исходного архива совпал. `scripts/backup-crypt.mjs decrypt INPUT OUTPUT KEY_PATH` создаёт новый файл и проверяет authentication tag; ключ не выводится. Не хранить единственный экземпляр ключа только на VPS. Регулярное внешнее хранилище пока не настроено.

При восстановлении: остановить bot/worker, закрыть целевой профиль, восстановить custom pg_dump через pg_restore в пустую БД с сохранением `_prisma_migrations`. Сначала проверить restore в scratch DB. Redis восстанавливать только в namespace CF, с теми же IDs и учётом TTL, без FLUSHDB shared Redis. Сверить logical hashes и физический UTC; затем PAUSED/DRY_RUN и только один polling.

## Откат

Старый VPS и его данные оставлены. Его bot/worker/AdsPower остановлены и отключены от автозапуска. Остальные проекты не менялись.

Перед возвратом остановить новые службы и сделать свежий согласованный snapshot: после переключения старые данные уже могут быть неактуальны. Перенести новые изменения назад, проверить UTC/очередь, закрыть профиль на новой машине, затем запустить старые службы. Никогда не включать два polling или два worker одной production-очереди. Для отката только кода предыдущий релиз V1.8 совместим с добавленными nullable/default полями, но новые взаимодействия до возврата нужно приостановить и сверить.

## Что ещё требуется для LIVE

Отдельное разрешение на конкретные внешние действия. OpenAI key/model/prices настроены в V1.9; это не разрешение на публикации. В исходной production-БД tracking_links была пустой, это состояние сохранено. Публичный tracking-домен/HTTPS пока не настроен; внутренний маршрут и атрибуция покрыты тестами. Нельзя считать `factory.invalid` рабочим публичным адресом. С V1.9 отдельная ссылка в CTA необязательна; фото загружается из Telegram с предпросмотром и отдельным сохранением. Ежедневный внешний encrypted backup требует отдельного storage destination.

При полном откате отдельно перенести актуальный локальный cache Threads 02 после закрытия браузера: cloud sync не считается резервной копией. Ежедневный PostgreSQL dump сам по себе не содержит browser cache и медиа-файлы; миграционный KEEP archive содержит исходное состояние этих файлов.

Telegram: RestartSec=10s и StartLimitIntervalSec=0 — длительный сетевой сбой не оставляет polling навсегда остановленным после ограниченного числа попыток. Ошибка токена требует обновления защищённого файла; значение токена в журнал не выводится.

## V1.12: ручные публикации

Текущий путь заменяет адресную операторскую настройку V1.11 для каждой задачи. Историческое описание ONE_SHOT выше относится к старым разрешениям и тестам, новые карточки его не используют.

Один раз на сервере подключается `/etc/content-factory/manual-settings.env` с `MANUAL_LIVE_ALLOWED=1`, `TELEGRAM_OWNER_ID` и `TELEGRAM_ALLOWED_IDS`. Файл не содержит API-ключей; права root:contentfactory 0640. Drop-in `60-manual-v112.conf` подключает одинаковую политику к bot/api/worker. Разовое открытие серверной возможности выполнено с отдельного разрешения владельца 20 ноября 2026, в 14:47 МСК. Сам manualLiveEnabled остаётся false до Telegram-подтверждения. Это только техническая возможность: в PostgreSQL `manual-policy-ACCOUNT.manualLiveEnabled` по умолчанию false.

Включение: «Аккаунты → Threads 02 → Публикации → Включить ручные → Разрешить», только владелец из allowlist в личном чате. Одна кнопка «Опубликовать» в новой карточке подтверждает выбранный текст, а у собственного поста также текущий CTA. Для новых версий не нужны SSH и изменения environment. Автоматические режимы продолжают DRY_RUN, автоматические публикации в V1.12 недоступны; старый backlog не запускается.

`automationPaused` останавливает планировщик; `factoryPaused` оставлен как совместимый дополнительный запрет. `emergencyStop` запрещает все внешние отправки, включая ручные и изменения профиля. Кнопка аварийной остановки доступна в настройках публикаций. При снятии ручные политики отзываются, требуется новое включение. Отзыв увеличивает epoch: прежние задания не оживают после повторного включения.

Карточки хранятся как `manual-card-*`, сессии `manual-session-*`, политики `manual-policy-*`, разрешения собственных постов `manual-post-*`, реплаев `reply-permission-*`. Сессии действуют 24 часа, разрешение конкретной отправки — 10 минут. Проверяются actor/allowlist/owner/account/hash/version/source/expiry перед отправкой; SENDING/UNCERTAIN и leases сохраняются. Отмена карточки работает до принятия публикации. После принятия можно отключить ручные публикации; уже выполненный submit требует проверки результата и не повторяется.

Диагностика после разового допуска: `python3 deploy/verify-v112.py --server-manual-allowed 1` (проверка требует выключенного manualLiveEnabled). Безопасная приёмка без второго polling и без LLM: `deploy/run-acceptance-v112.py` (сначала cards, отдельно V112_PHASE=dry). Тесты PostgreSQL/Redis запускаются только через изолированный `deploy/test-isolated-v18.py`. Реальную отправку после установки оставить выключенной. Для установки серверного допуска только после отдельного разрешения владельца служит `deploy/allow-manual-server-v112.py`; он не включает ручную политику аккаунта, проверяет неизменность публикаций и откатывает файл окружения при ошибке.

## V1.13–V1.14: свежесть, происхождение и стиль

Происхождение сохраняется при подготовке исходника, отдельно от одобрения текста. Новые материалы требуют фактического выбора OWN/PERMITTED; THIRD_PARTY/UNKNOWN не дают права отправки. Для неполученного URL использовать проверку существующего результата, сохраняя UNCERTAIN и не повторяя submit. Отдельная CTA-карточка для уже подтверждённого поста не создаёт основной пост заново. Детали и pending CTA: [V1.13](V1_13_REPORT.md).
