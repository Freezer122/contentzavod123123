# Content Factory V1.1 — исторический отчёт

Актуальные [правки перед запуском V1.2](PRELAUNCH_REPORT.md) имеют приоритет: 12-минутные слоты, CTA при первом старте задачи и возможность его отключения. Ниже сохранена история предыдущей версии.

Обновление внесено в существующие модули. Данные V1.0 сохраняются; новая SQL-миграция добавляет поля и четыре таблицы: кэш адаптаций, признаки контента, зашифрованные идентификаторы участников и когорты Telegram. Исходная миграция не менялась.

## Режимы

Основной — ACCOUNT_SPECIFIC. В «Создать публикацию» выберите «Отдельный пост каждому аккаунту». Нажмите аккаунт, отправьте его исходник и подтвердите права. Назначьте следующие материалы другим аккаунтам. Только кнопка «Подготовить назначенные посты» запускает генерацию. Один исходник не назначается двум аккаунтам в этом режиме.

BROADCAST: отправьте один исходник, выберите аккаунты и настройку. COMMON создаёт один текст с голосом первого выбранного стиля и с общими ограничениями длины/абзацев/эмодзи/запрещённых выражений. PER_ACCOUNT одним пакетным запросом создаёт варианты для разных стилей. Одинаковые стили и готовые результаты повторно используются. Оба режима требуют предпросмотра и подтверждения партии.

Кэш учитывает исходный текст, версию инструкции, API endpoint, модель, температуру, лимит токенов, режим и фактически используемые параметры/примеры стиля. Он хранится в БД. Проверки формата выполняются TypeScript; невалидный ответ остаётся черновиком и не вызывает дополнительный автоматический запрос. Ручная кнопка «Перегенерировать» разрешает новый запрос. Изменение общего текста через редактор COMMON применяется ко всем выбранным черновикам. Семантика и качество стиля по-прежнему требуют просмотра человеком.

## Цикл и CTA

Для N аккаунтов интервал = 7200 / (N − 1) секунд. При N=10 — 800 секунд; первый и последний плановые старты разделены 120 минутами. При N=1 интервал равен нулю. Это целевой график стартов, а не гарантия завершения всех действий при задержках, проверках платформы или простое сервера.

Сохраняются исходный план, фактический первый старт задачи, последняя попытка, отклонение и причина задержки. Задачи партии выполняются по порядку. Профильные и общие браузерные блокировки сохраняются. Старые сохранённые расписания автоматически не сжимаются до нового окна. Команда `/interval` больше не задаёт случайный интервал.

У каждого аккаунта отдельный активный CTA: текст, HTTPS URL, версия и дата изменения. Путь: «Аккаунты → аккаунт → Редактировать CTA», затем два сообщения — текст и ссылка. В задачи копируются все поля версии. Последующая правка не меняет подготовленные задачи и опубликованную историю. `/cta_template` копирует текст в собственный CTA, а не назначает один общий объект нескольким аккаунтам. Отключение CTA заменено паузой аккаунта.

Комментарий отправляется не раньше чем через 20 секунд после подтверждения поста. После перезапуска ожидается только оставшаяся часть задержки. Элементы интерфейса ожидаются Playwright. Известная ошибка до отправки комментария получает COMMENT_FAILED; сам пост остаётся PUBLISHED. При неизвестном результате отправки сохраняется UNCERTAIN и ручная проверка — автоматического повтора нет. Найденный собственный CTA не отправляется повторно.

## Аналитика и рейтинг

Контрольные снимки: 1, 6, 24, 72 и 168 часов. Старый снимок 48 часов и прочие метрики сохранены. Нет источника — значение NULL. Позднее измерение сохраняет реальное время и не выдаётся за результат ровно на целевой отметке.

Content Performance Rating хранит исходный/итоговый текст, тему, формат, хук, длину и вопрос. Начальные признаки определяются простыми правилами. Вручную: `/tag SOURCE_ID {"topic":"Риск","format":"Разбор","hook":"Вопрос"}`. Признаки копируются при публикации. Доступны лучшие посты, просмотры за 24 часа, средние и медианные результаты тем и форматов.

Сравнение проводится по выбранной общей контрольной отметке 1/6/24/72/168 часов. Старый пост не получает преимущество из-за большего срока накопления просмотров. Нет своевременного сопоставимого снимка — пост исключается из этого рейтинга. Прирост Threads относится к аккаунту за измеряемое окно; это не доказательство подписки из конкретного поста. Переходы и вступления в карточке — только контекст аккаунта, постовые значения остаются NULL.

## Постоянные ссылки и когорты Telegram

Один постоянный redirect URL и одно активное приглашение на аккаунт. `/link` сохраняет код при смене назначения, `/invite` повторно использует существующее приглашение. Исторические ссылки продолжают работать; события не удаляются. Новая привязка к postId отклоняется: атрибуция только ACCOUNT_ONLY.

Каждое вступление хранит дату, источник и историю статусов. Повторное вступление создаёт новую когорту. Выход связывается с предыдущим наблюдаемым эпизодом подписки; неизвестный источник не угадывается. Для `getChatMember` Telegram user ID хранится зашифрованным AES-256-GCM. Ключ выводится из TRACKING_HASH_SECRET с отдельным назначением; сырой ID, IP и User-Agent не записываются в логи. Этот секрет нельзя менять без миграции хешей и зашифрованных идентификаторов.

D7 и D30 проверяются через Bot API при наличии ID и прав бота. Целевая проверка выполняется в пределах часа после контрольной даты; время измерения сохраняется. Поздний запрос текущего членства не подтверждает историческое D7/D30 и остаётся NULL. Подтверждённый выход до контрольной даты даёт известный отрицательный результат. Исторические события V1.0, содержащие только необратимый хеш ID, нельзя задним числом проверить через API.

Retention = оставшиеся / зрелые когорты × 100; Churn = вышедшие / зрелые когорты × 100. Пока хотя бы одна зрелая когорта не проверена, итоговый процент неизвестен. Отдельно показаны зрелые, проверенные, оставшиеся, вышедшие и неизвестные; доля среди проверенных доступна в API. Клики и вступления не смешиваются. Панель когорт по умолчанию использует всю историю: у вступивших за последние семь дней ещё нет D7.

Официальная возможность проверки: [Telegram getChatMember](https://core.telegram.org/bots/api#getchatmember). Для проверки других пользователей бот должен иметь необходимые права администратора. Длительные пропуски Telegram-событий не восстанавливаются вымышленными значениями.

## Обновление

```bash
# Остановите приложение и сделайте резервную копию по docs/DEPLOYMENT.md.
npm ci
npm run db:migrate
npm run check
# Перезапустите приложение.
```

При первом запуске персонализируются старые общие CTA и выбираются постоянные аккаунтные ссылки. Снимки CTA в старых задачах остаются прежними. Проверьте тексты, ссылки и настройки канала до реальной публикации.

Для полной интеграционной проверки задайте TEST_DATABASE_URL и TEST_REDIS_URL. Тесты используют отдельную временную SQL-схему и очередь. Нужен установленный Playwright Chromium. Проверки работают без реальных Threads-аккаунтов и без платных LLM-запросов.

Реальная приёмка остаётся внешней: авторизованный AdsPower/Dolphin профиль, текущие селекторы Threads, Telegram-бот и канал с правами, домен/TLS, LLM и Insights. Ни одна локальная проверка не подменяет публикацию на вашем аккаунте.

## Результаты проверки поставки

- Пройдены все 55 автоматических тестов, форматирование, TypeScript и production-сборка.
- Проверки выполнены с настоящими PostgreSQL, Redis и Chromium. Реальные Threads-аккаунты не использовались.
- Prisma migrate deploy применил обе миграции; в БД 28 прикладных таблиц и таблица учёта миграций. Проверено сохранение старого CTA-снимка, отменённой задачи и tracking-кода.
- Собранное демо проверено HTTP-запросами: ACCOUNT_SPECIFIC, оба варианта BROADCAST, окно 120 минут для двух аккаунтов, десять индивидуальных CTA, рейтинг и endpoint когорт.
- Реальная задержка комментария в демо составила 20,022 секунды; изменение CTA после создания задачи не поменяло применённый снимок.
