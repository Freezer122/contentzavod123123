# Engagement Manager V1.8

Отдельные EngagementManager, EngagementQueue и browser port; PublishingWorker собственных постов сохранён. Очередь взаимодействий хранится в PostgreSQL как документы system_settings; Redis/BullMQ продолжает обслуживать исходную очередь публикаций. Lease, транзакции и audit общие с действующей системой.

В Telegram: «Аккаунты → аккаунт → Взаимодействия». Настройки: включение, категории, слова, ответы/лайки в сутки, min/max интервал, максимум кандидатов, сессии в сутки, лайки, дневной/месячный бюджет LLM. Доступны поиск, кандидаты, ручные/сгенерированные черновики, одобрение/редактирование/отклонение, история, статистика и расходы.

Начальные настройки: выключено; трейдинг; 3 короткие поисковые сессии в сутки; до 30 активных кандидатов; 3 ответа и 3 лайка/сутки; интервал 60–180 минут; лайки выключены. Поиск — до трёх навигаций по ключевым словам за сессию, без постоянной ленты и LLM.

## Фильтрация и ответы

Сохраняются canonical URL, автор, текст, язык, категория и время обнаружения. Обычный TypeScript отбрасывает дубли, собственные/обработанные/пустые/неподходящие публикации, нерусский текст и недоступную кнопку ответа. Категории определяются по словарям, не моделью. Детерминированный ID обеспечивает дедупликацию для аккаунта.

Модель получает только выбранный пост, один короткий запрос. Используются существующий ContentEngine, резерв бюджета, назначения расходов, кэш и TextNormalizer. Новые числа/тикеры вне исходника, рекламные ссылки и повторные ответы блокируются. Ручной ответ работает без модели. Любой ответ требует одобрения показанного текста и URL; редактирование отзывает одобрение. Лайк имеет отдельное подтверждение.

## Безопасность очереди

Собственные публикации и CTA имеют приоритет. Поиск уступает браузер при появлении срочной publishing job; после submit подтверждение ответа завершается в занятой сессии. Глобальный browser-slot и profile lease ограничивают систему одним браузером. Все действия одной операции используют уже открытый owned context; чужая или вручную открытая сессия не захватывается и не закрывается.

SENDING сохраняется до первого клика отправки. Неопределённый результат и прерванный SENDING становятся UNCERTAIN, автоматически не повторяются. Для реальной отправки проверяются фабрика, аккаунт, одобрение, интервалы и лимиты. Тестовые акторы не могут отправлять реальные взаимодействия. По умолчанию `ENGAGEMENT_EXECUTION_MODE=DRY_RUN`; для LIVE также нужен LIVE publishing execution. При PAUSED автоматические поиск и обработка не запускаются.
