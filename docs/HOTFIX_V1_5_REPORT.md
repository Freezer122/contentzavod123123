# Content Factory — Hotfix V1.5

Дата: 19 ноября 2026. Установлен на Ubuntu VPS в `/opt/content-factory/releases/20261119-hotfix-v15`; `/opt/content-factory/current` указывает на этот release.

**Бот работает автономно, worker оставлен DRY_RUN, завод и Threads 02 — PAUSED. Новых реальных постов и комментариев не публиковали.** В production-БД по-прежнему один ранее опубликованный пост и один CTA, LLM-запросов — 0. Thread 01 не запускался и не изменялся.

## 1. Причины задержки и исправление CTA

Первая публикация успешно прошла на стороне Threads, но первоначальная проверка ожидала новый результат на текущей странице. После отправки поста страница профиля ещё не показывала его; после CTA текущий тред также не дал подтверждение за прежний срок. Оба результата удалось надёжно подтвердить отдельным чтением собственных permalink. Защита UNCERTAIN правильно остановила повторы, однако потребовалась ручная сверка.

Дополнительную задержку создавал сам worker: двадцать секунд отсчитывались от **подтверждения URL**, а редактор и вложение CTA готовились только после ожидания. Медленное подтверждение автоматически сдвигало весь цикл.

Теперь:

1. До единственного клика сохраняется durable SENDING barrier. После выполнения клика фиксируется наблюдаемый `post_submit_at`.
2. Сначала проверяется непосредственно post-submit интерфейс. Собственный permalink из status/alert или текущего URL рассматривается как кандидат и проверяется чтением текста и аккаунта. Само сообщение об успехе не считается достаточным доказательством.
3. Короткий опрос интерфейса — 2,5 секунды; резервное повторное чтение профиля/треда выполняется примерно раз в два опроса. При наличии прямого permalink предпочтительно чтение по нему. Лимит 90 секунд остаётся защитным пределом, а не основным способом подтверждения.
4. CTA назначается на `post_submit_at + 20 секунд`. После подтверждения поста сразу открывается редактор и загружается вложение. Ожидание оставшегося времени происходит непосредственно перед отправкой CTA, вне транзакции БД.
5. Если подтверждение или подготовка завершились позже назначенного времени, дополнительного двадцатисекундного ожидания нет. CTA отправляется после надёжного подтверждения поста; опоздание сохраняется в телеметрии.
6. При интервале более 45 секунд без CTA создаётся CTA_DELAY и уведомление владельцу. Проверка выполняется каждые пять секунд и при восстановлении задачи; повторное уведомление по той же задаче блокируется сохранённым маркером.

В `publishing_jobs` отдельно сохраняются:

| Поле PostgreSQL / API | Значение                                         |
| --------------------- | ------------------------------------------------ |
| `post_submit_at`      | Завершение клика отправки поста в Playwright     |
| `post_confirmed_at`   | Надёжное подтверждение текста и собственного URL |
| `cta_scheduled_at`    | Целевое время CTA                                |
| `cta_submit_at`       | Завершение клика отправки CTA                    |
| `cta_confirmed_at`    | Подтверждение текста, URL и вложения CTA         |

До наблюдения завершённого клика barrier содержит резервное время начала отправки. При сбое результат остаётся UNCERTAIN; этот резервный timestamp не даёт разрешения создавать CTA. Внутреннее время серверов Meta не предполагается известным. Для старой первой публикации недостающие timestamps не выдумывались.

`actual_interval_seconds` = CTA submit − post submit. `cta_lateness_seconds` = положительная разница CTA submit и назначенного времени. Показатели отображаются в `/queue` для активных задач и последней завершённой, а также в существующем `/api/queue`.

Защита от дублей, leases, раздельные состояния поста/CTA, повтор только известной неотправленной CTA и перевод SENDING в UNCERTAIN при сбое сохранены. Под неподтверждённым постом CTA не создаётся.

## 2. UTC: найденная ошибка физического хранения дат

Независимая проверка через PostgreSQL выявила сдвиг **−10 800 000 мс**: прежний Prisma adapter показывал приложению правильную ISO-дату, но при timezone Europe/Moscow физическое значение сохранялось на три часа раньше. Простое сравнение Prisma → Prisma эту ошибку не обнаруживало.

Соединения приложения теперь явно используют `timezone=UTC`. Для этого конкретного проверенного legacy-развёртывания выполнена opt-in миграция `202611190003_utc_timestamps`. Сравнение всех **31 прикладных таблиц** до и после показало `logicalTimestampsPreserved=true`, без отличающихся таблиц. История сохранила значения, которые ранее видело приложение. Таблица служебных миграций не сдвигалась; на новой БД без проверочного маркера преобразование данных не выполняется.

После исправления независимое сравнение физического epoch и даты приложения даёт **0 мс разницы**. Добавлена проверка реального PostgreSQL, а не только типа Date. Сохранены dump перед нормализацией и закрытый логический снимок:

- `/var/lib/content-factory/backups/before-v15-utc-normalization.sql`
- `/var/lib/content-factory/backups/v15-timestamp-logical-snapshot.json`

При откате требуется согласованность версии приложения и UTC-настройки; старый adapter без UTC нельзя просто подключать к нормализованным данным.

Также повтор транзакций теперь распознаёт `DriverAdapterError / TransactionWriteConflict` наряду с Prisma P2034. В старых журналах этот вариант ошибки встречался при фоновых операциях.

## 3. Telegram

Причина отсутствия ответов: был запущен только PROCESS_ROLE=worker, в его конфигурации отсутствовали токен и allowlist. Обработчик меню и команд уже существовал; отдельной действующей bot-службы не было. getMe проверял только токен, но не обеспечивал получение сообщений.

Использован предоставленный пользователем действующий токен. Он сохранён только в `/etc/content-factory-secrets/telegram.env` с правами 600, каталог — 700. Allowlist находится в `/etc/content-factory/telegram.env`, доступ разрешён одному указанному пользователем ID. Значение токена отсутствует в коде, документации и диагностических выводах.

Новая служба `content-factory-telegram.service`:

- использует существующий `createBot` и отдельную роль `bot`;
- не запускает HTTP-сервер, потребителя публикаций, сбор аналитики или retention;
- работает через long polling, с файловым flock и Restart=on-failure;
- включена в multi-user.target для автозапуска;
- проверяет отсутствие webhook до начала polling;
- завершает процесс при фатальной остановке polling для восстановления через systemd;
- пересылает сохранённые уведомления worker разрешённому владельцу с устойчивым курсором доставки.

Telegram не выдаёт getUpdates при установленном webhook, поэтому проверка режима сделана до запуска. Основание: [Telegram Bot API](https://core.telegram.org/bots/api#getwebhookinfo). Обработка ошибок polling согласована с [grammY](https://grammy.dev/guide/errors).

| Проверка                      | Фактический результат                                                                                                        |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `/start`                      | Обработаны три реальные накопившиеся команды владельца                                                                       |
| `/ping`, `/status`            | Пользователь подтвердил получение обоих живых ответов                                                                        |
| `/accounts`, `/queue`         | Существующие обработчики проверены тестовыми update; Telegram принял реальные ответы владельцу, второй polling не запускался |
| Редактирование CTA            | Полный существующий flow редактирования, предпросмотра и сохранения проверен в изолированной БД; production CTA не менялся   |
| Посторонний ID                | Команда не получает доступ; проверено автоматическим тестом                                                                  |
| Аварийное завершение процесса | systemd автоматически запустил новый процесс                                                                                 |
| Уведомление после сбоя        | Тестовое уведомление доставлено после восстановления, курсор сохранён                                                        |
| Конфликты                     | Webhook отсутствует, pending updates 0, один живой Node-процесс с этим токеном                                               |

Полную перезагрузку общего VPS не выполняли. Автозапуск включён, восстановление после аварийного завершения процесса проверено фактически.

## 5. Производительность без увеличения ресурсов

VPS остался 2 vCPU / 4 GiB RAM. Одновременно работали Telegram, worker, PostgreSQL, Redis, AdsPower и **один SunBrowser**. Через Playwright читался ранее опубликованный пост; редакторы и submit не использовались. Второй профиль и второй тестовый браузер во время замера не запускались.

Окно — 51,448 секунды, 47 отсчётов /proc. CPU нормирован на весь сервер, RAM учитывает MemAvailable; показатели включают другие приложения VPS.

## 6. Проверки и ограничения приёмки

- Полный серверный набор: **87 / 87** тестов.
- Дополнительно два новых браузерных regression-теста: permalink из post-submit UI и отсутствие надёжного результата с единственным submit — оба пройдены. Итого 89 проверенных автоматических тестов; два последних запускались отдельно.
- Восемь сценариев worker DRY_RUN пройдены; реальные часы и изолированные перехваченные страницы, без реальных профилей/публикаций/LLM.
- Нормальный DRY_RUN: `post_submit_at=10:50:16.336Z`, `post_confirmed_at=10:50:21.476Z`, `cta_scheduled_at=10:50:36.336Z`, `cta_submit_at=10:50:36.372Z`, `cta_confirmed_at=10:50:36.396Z`. Интервал кликов **20,036 с**, опоздание **0,036 с**. Интервал запросов изолированной фикстуры — 20,034 с.
- Автотесты подтверждают: confirmation 3 с + подготовка 5 с → submit CTA на 20-й секунде; confirmation 30 с + подготовка 2 с → на 32-й, без новых двадцати секунд; confirmation 50 с → уведомление; UNCERTAIN → без CTA и без повтора поста.
- Проверены восстановление очереди PostgreSQL/Redis, защита от дублей, закрытие сессий, устойчивость уведомлений при ошибке и одинаковых timestamps, CTA UI и allowlist.
- Format check, TypeScript, production/tool builds успешны. Новые секреты в исходниках и документации не обнаружены.

Осталось проверить новый быстрый путь подтверждения и интервал CTA в **следующем отдельно разрешённом реальном посте**. Сейчас это подтверждено изолированными тестами и read-only проверкой существующего поста. Новых реальных публикаций в рамках hotfix не было.

Финально: bot active/enabled, worker active/enabled в DRY_RUN, factoryPaused=true, Threads 02 PAUSED, один прежний пост и один прежний CTA, LLM 0, браузер закрыт. Одноразовый LIVE gate не создавался.

Артефакты: `/var/lib/content-factory/reports/` на VPS и `.local/hotfix-v15/` локально. Резервные копии перед миграциями — `/var/lib/content-factory/backups/`.
